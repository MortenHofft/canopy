# Phylocanvas.gl 1.64.1 (2026-10-14)

Spike: `spikes/phylocanvas-gl/` (React wrapper `src/adapter.tsx`, CPU hit-testing `src/hit.ts`, own deck.gl layers `src/layers.ts`, Newick-to-biojs `src/source.ts`, metadata `spike.json`, probes `scripts/`). Runs: `spikes/results/phylocanvas-gl/`. Machine: 4 CPU Xeon 2.8 GHz, 16 GB, headless Chromium 141 **without GPU (SwiftShader)**, shared with five other agents (**load average 2 to 18 while developing, 3 to 5 during the final runs listed below**). Library source read from the npm 1.64.1 source maps (177 files extracted; paths below are `source/...` inside the package, line numbers from that extraction) and run in a browser. deck.gl **8.8.27** (exact; see "What surprised us" for why not 8.9).

**How to read the numbers.** There is no GPU here, so every WebGL frame is software-rendered and every FPS figure below is pessimistic and says little about a laptop. Two things are independent of that and are the useful ones: the JavaScript main-thread cost per interaction (setProps, restyle, hit-test, parse and layout: measured by `scripts/scale-probe.mjs`, labelled "probe") and what the library can or cannot do at all. The runner's S1 statuses for WebGL are all `timeout` for that reason, including the 5-tip tree. A Canvas2D reference of the same scene (`scripts/canvas2d-ref.html`, CPU raster) was driven by the same scripted input in the same browser to put the numbers in context.

Gates: **G1 pass** (library MIT, `LICENSE`, Centre for Genomic Pathogen Surveillance; production dependency graph of 32 packages walked from `package.json` files: 30 MIT, `@mapbox/tiny-sdf` BSD-2-Clause, `earcut` ISC; no GPL or LGPL; README Q7 reserves the Phylocanvas name and logo, so a fork must be renamed). **G2 pass** (static files; WebGL required, no canvas fallback). **G3 pass with flags**: an imperative class (`new PhylocanvasGL(element, props, plugins)`), no React component, no bundled types, peer `deck.gl ^8.8.12` whose upper part (8.9.x) crashes at load (below); a thin wrapper gives clean mount and unmount (S13 pass, 24 cycles, two instances). **G4 flag**: release 1.64.1 on 2026-07-13, six releases since 2025-12-10 (npm registry, re-read 2026-10-14), but one developer, no tags, issues on a separate tracker, and the README (Q7) says "feature complete" and "unable to provide support".

## Library features tried through the demo (manual, Playwright scripts against the built page)

Run by `scripts/feature-checks.mjs` (output `spikes/results/phylocanvas-gl/feature-checks-20261014.json`) unless noted.

Works:
- **Five layouts** (`?pc.treeType=rc|cr|rd|dg|hr`): for the 200-tip tree `locate()` and the own hit-test agree for all 198 internal nodes and all 200 tips in every layout (rc, cr, rd, dg, hr: 198/198 and 200/200). Radial (rd) and circular look right (screens), the shell's "radial" tab is mapped to circular.
- **Re-root view** (`rootId`, Library option): clicking the branch of a 38-tip clade leaves exactly its 38 leaves drawn (id `__324`); clearing the switch restores the tree.
- **Collapse** (`collapsedIds`, `showPiecharts: true`): clades under 20 tips collapse to 16 pie charts; a click on one gives `nodeClick` with its 3 tips. Without `showPiecharts` the library skips styling inside collapsed clades, so their pies have no colours.
- **Native parser versus biojs object**: the same 7-tip Newick with `'a,b(c)'` gives 8 tips with the library's tokenizer and 7 with our object; the mapping check flags it ("NOT exact, 1 mismatch") and the wrapper falls back to tip-set search.
- **Library blocks mode** (`?pc.columnMode=blocks`, screen `demo-4`): one coloured square per cell with rotated headers, `locateCell` from `pixelOffsets.length + blockPadding + n * columnWidth`; bar values become opacity of the GBIF green. Squares shrink vertically below the block size and rows cannot be summarised.
- **Tip marker shape and size, branch width 1 to 3 px, label size 10 to 16 px, labels off, internal labels, branch-length labels, align labels**: library props, switched from the Library options card (looked at, no runner scenario).
- **Hover**: pointer over a branch recolours the whole clade and its labels in `--color-primary` (library `highlightedId`); the shell's tooltip shows the tip count (events carry at most 2,000 tip ids for a hovered clade).
- **Mount and unmount**: 24 cycles with and without the explicit context release: no "too many contexts" message, canvases 0, heap 10.8 to 11.6 MB; `destroy()` alone leaves `isContextLost()` false, our `loseContext()` makes it true.

Breaks or surprises:
- **deck.gl 8.9.x** (see A and "What surprised us").
- **Library GPU picking** is slow or lost in software GL from 10k tips (C picking).
- **Non-ASCII labels**, **trimQuotes**, **tokenizer**, **stale edge colours**, **label background colour type** (G, D, C rows).
- **Marker size is in pixels**: at the fit view of a dense tree markers overlap into a solid bar (the demo picks 10, 6, 3 or 2 px from the tip count and enlarges after `focusTip`); nothing scales with the rows.
- **Wheel**: the library zooms both axes, which pushes the tip column out of view after a few notches; the demo's row zoom fixes this up to 20k tips and costs O(n) per step.
- **Columns reserve their width through a dummy metadata block** (`blockSize = total width`): if the library changes how it sizes the drawing area, columns overlap the tree. Columns exist only in the rectangular layout.
- **`hiDpi` option** (`deck.setProps({ useDevicePixels: true })`): switched on in the card but not looked at (device pixel ratio is 1 in every run here) (U).
- The CGPS logo is a `background-image` data URL on the host element; it overlaps the bottom-right corner unless removed.

## Differences from `docs/research/phylocanvas-gl.md`

Confirmed: MIT, WebGL through deck.gl, no callbacks, leaf-only selection, synthetic internal ids `__<preorder>`, `decorate` as the only event route (works in 1.64.1 for `selectNode`, `highlightNode`, `handleClick`, `render`), `styleNodeEdges` rule (internal edge coloured only if all children agree), coloured-square columns only, `addLayer` as a real extension point, logo background to remove, weak Newick tokenizer, deck.gl 8 pin.

Corrections and additions:

1. **Internal nodes are observable, not only leaves.** The note says "only leaf nodes can be selected" and lists node objects as missing for the host. Selection is leaf-only (`select-node.js:28`), but `selectNode` is *called with* whatever deck picked, so the decorate plugin receives internal node objects (edge picks, collapsed-clade pie picks) with `children`, `totalLeaves`, `preIndex`. What is missing is the tip list and any internal marker, not the node.
2. **Several trees per page work.** The note (Risks 3, scorecard 12) says one WebGL context per page and multiple trees unsupported. Each instance builds its own `Deck` and context (`methods/init.js`); two instances ran side by side (S13). The README sentence is about one canvas per instance.
3. **Peer range is wrong at the top.** `deck.gl ^8.8.12` admits 8.9.x, which crashes at module evaluation (TypeError on `componentName`); 8.8.27 (the last 8.8) works and 8.9.36 (the last 8.x, `v8-latest`) does not (open question "which deck.gl 8 minor": answered). deck.gl 9 is still unknown (U).
4. **Focus recipe works** (open question): `stepZoom` for the row axis plus `centre` from the node's world `y` and the library's own `target <-> centre` maths, batched with `suspend()`/`resume()`. A `centre` at normalised space needs `getDrawingArea()` and `getCanvasSize()`; see `focusTip` in `adapter.tsx`.
5. **Layout cost is linear and measured** (open question about 1M): parse plus layout in the constructor is 0.37 s at 1k, 0.22 s at 10k, 0.97 s at 50k, 2.1 s at 100k and 3.2 s at 190k (probe v2, load 3 to 5); the row axis zoom repeats a full layout per wheel step (22 ms at 10k, 249 ms at 100k). Not measured above 190k; the 1M target stays open.
6. **Edge level of detail does not exist in 1.64.1.** The note lists `edgeOverlapFactor` sub-pixel skipping; the option is declared in `defaults.js` and never read. Only label thinning and manual collapse remain.
7. **Metadata blocks are not culled** (open question): `blocks-data.js` emits one datum per tip and column at every zoom; they are square-capped by `maxSizeRatio` when rows are smaller than the block.
8. **`destroy()` does not release the GL context** and leaves canvas, host styles and logo (confirms the note's source reading, adds the context result); the docs claim it removes the canvas.
9. **The weak Newick parser has a second hazard** beyond the note's: the default `trimQuotes` changes labels that start or end with a quote character (a real OpenTree label), and the regex tokenizer turns a quoted label containing `,` or `(` into extra tips. `trimQuotes: false` and a pre-parsed `biojs` object avoid both.
10. **Non-ASCII labels** (not in the note): dropped as shipped (ASCII glyph set); fixable with a one-line page-wide patch of deck.gl's `TextLayer` default.
11. **Stale edge colours** (not in the note): changing only `styles` does not recolour edges (accessor memo); needs a new `strokeColour` array identity. The note's `styleNodeEdges` description stays correct.
12. **Label background must be an RGBA array** (a CSS string draws black boxes), while every other colour prop takes CSS strings (`layers/leaf-labels/index.js` hands `backgroundColour` to deck.gl unconverted).
13. **The library tooltip is the browser `title` attribute** (`set-tooltip.js:26`, random zero-width suffix to force updates): not styleable; the shell's tooltip is fed from hover events instead.
14. **Wheel semantics:** plain wheel zooms both axes, shift or alt stretch rows, ctrl or meta stretch branches (`utils/create-controller.js`); at the fit view the plain wheel never keeps rows and columns together, which is why the demo reroutes it to row zoom.
15. **Picking is synchronous and per pointerdown** (deck.gl `_onPointerDown`): the note's "leaf labels pickable" is right, but the cost model matters: a pick is a full GPU pass plus readback (55 to 150 ms at 1k tips, 0.5 to 0.7 s at 10k, 5 to 6 s at 100k in software GL), executed in the pointerdown handler, which is why the demo ships its own CPU hit-test.
16. **~100-line wrapper:** true for construct, setProps, plugin events, destroy. A wrapper that also does clade colouring, ids, focus, columns, links, keyboard and hit-testing is about 1,560 lines here (962 adapter incl. about 110 lines of capability text, 318 layers, 237 hit-test, 45 source).

## Verdict

1. Phylocanvas.gl is the only WebGL candidate and the one that comes closest to scale on paper (uniform zoom costs 0.4 to 0.7 ms of JS at any size, parse plus layout 3.2 s and 590 MB at 190k tips), and it has native clade hover, collapse with pie charts, five layouts and a documented layer extension point; but its GPU speed could not be measured here (software GL: 0.1 ms per tip per frame), so the "100K+" claim stays unconfirmed.
2. Everything gbif.org needs beyond drawing is our code on a library with no callbacks: events, internal-node clicks and ids, hit-testing, clade colouring (two workarounds), focus, columns and alignment, links, keyboard, cladogram, scale bar, unicode labels, context release: about 1,560 lines and eight workarounds, all working (S2, S4 to S9, S11 to S14 pass; S3 and S15 partial by rule), on a deck.gl 8 pin (8.9 breaks it), a vendor that offers no support, and no level of detail or overview.
3. Choose it only if a measured GPU result at 100k tips with columns is a hard requirement and a fork is acceptable; for tables of 100 to 20,000 tips the custom canvas baseline does the same with less coupling, and for trees that need clade summaries at the fit view neither exists yet.

## What surprised us

- **deck.gl 8.9, inside the declared peer range `^8.8.12`, kills the library at load** (a TypeError while the bundle evaluates). 8.9.x is also the last 8.x line on npm (`v8-latest` 8.9.36). Pinning 8.8.27 is mandatory and invisible to anyone who just installs the peer.
- **Clicks vanish in software GL with the library's own picking** (at load 9 and from 10k tips). deck.gl does a synchronous GPU pick on every pointerdown; the click recogniser (mjolnir/Hammer, 250 ms) measures from before that pick, so a slow pick turns a click into nothing, while hover (picked per frame) keeps working. On a GPU this is probably invisible, which is also why we cannot confirm the library's claim about large trees: pick cost and frame cost are both GPU questions.
- **Software-GL frames cost about 0.1 ms per tip** (127 ms at 1k tips, 1 s at 10k, 11 s at 100k, 20.6 s at 190k): the same order as a Canvas2D page drawing the whole tree unculled on the CPU (14 s at 190k). Both need level of detail, not just a faster loop, to show 100k tips at the fit view without a GPU.
- **The library is quietly lossy about labels:** tip names starting or ending with a quote lose it (a real OpenTree label), quoted labels with delimiters split into extra tips, accents and CJK glyphs are not drawn. All fixable, none documented.
- **Edge colours go stale** when only the styles change. The fix we found (a new `strokeColour` array identity) is a side effect of how `colourToRGBA` caches, not an API.
- **Hovering a branch recolours the whole clade for free** (library `highlightedId`), which is the nicest clade interaction any candidate gave us without code; clicking it is the part that needs our hit-test.
- **Row zoom costs a full re-layout per wheel step** (128 ms at 50k tips, 249 ms at 100k, 575 ms at 190k) while the uniform zoom costs under 1 ms: the table-like zoom that GBIF would want is the expensive one.
- **Several instances per page work**, contrary to the research note, and unmount is clean enough (no context warning in 24 cycles) although `destroy()` leaves the context and the canvas.

## For `shared/` and `runner/` (reported to the main session)

- **S14** counted the same canvas three times: `tabAtFit` lists `canvas, canvas, canvas` (also reported for react-bio-viz with its toolbar button), so "Tab reaches at least 3 focusable elements" passed before any tip row existed and the focusTip fallback was skipped. Count distinct elements and require at least one tip or row.
- **S1 / S10 FPS**: the same scripted input gives a plain Canvas2D page (drawing 1k tips in 0.5 ms) p5 6.7 fps and the Phylocanvas page 3 to 6.7 fps at 1k tips, 0.9 against 0.4 to 0.7 at 10k; p5 of a 5-tip tree ranged 4 to 20 fps between runs at load 3 to 5. The rule measures compositor and input pacing in this sandbox more than the viewer, so statuses for any canvas or WebGL candidate are noise; a CPU-time rule (main-thread task time per interaction, as the tbrowse report uses) or best-of-N would be meaningful.
- **S7 / S8** require 8 visible cells after 8 plain wheel notches, which favours viewers by their zoom factor per notch: with the library's own both-axes wheel (x1.54 per notch) the tip column left the view and 0 cells were visible (fail on that count); with our row zoom at x1.54 per notch the 197-tip tree left 7 rows (S8 `partial` on the count alone, alignment itself 7/7 at dy 0.0); at x1.29 per notch (final) 46 and 28 cells pass. Consider zooming until a target row height instead of a fixed notch count.
- **Capability keys:** `descendantTipsInPayload` and `internalNodeClick` are coupled in the scoring (S3 `partial` whenever the tip set is adapter-derived, even if the node identity comes from the library). A separate "node reported by library" line would keep the information.
